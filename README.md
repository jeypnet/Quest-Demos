# Quest-Demos

**AI products / technical sales · Generated demo artifact**

This project shows how I evaluate an AI product and explain its output to technical buyers. My contribution was running the design-to-code workflow, demonstrating the result, and discussing implementation tradeoffs. The React components are generated by Quest, not presented as hand-written work.

**Recruiter takeaway:** customer discovery, technical demonstrations, AI-output evaluation, and communication across design and engineering. This is a single-card sandbox, not a complete production application.

**Sandbox output from Quest.ai, an AI platform that generates production React from Figma designs.**

I held a Sales Executive role at Quest.ai, where I demoed the platform to enterprise buyers. To demo it credibly I had to actually run it: push a design through the generator, export the result, and understand what the AI produced well and where a front-end team would push back. This repo is that sandbox, kept as-is.

Every file here carries a `generated by Quest` header. Almost none of it was hand-written, and that is the point.

## What the generator produced

```
src/
├── App.tsx                              # renders the generated card
└── components/
    ├── ProductCard1.tsx                 # generated component, MUI + emotion styled primitives
    ├── useProductCard1.ts               # generated logic hook, data and handlers live here
    ├── types.ts                         # generated prop interfaces
    ├── MyDesignSystemLightTheme.ts      # design tokens exported as an MUI theme
    ├── MyDesignSystemDarkTheme.ts       # dark variant of the same token set
    └── assets/
```

**Stack:** React 18, TypeScript 4.8, MUI 5, Emotion, Create React App.

## What is interesting about the output

**Design tokens survive the trip.** The Figma design system exports as a real MUI theme through `createTheme`, including non-standard tokens the generator carried through as custom entries:

```ts
customShadows: {
  "shadows":  { "boxShadow": "0px 3px 12px rgba(0, 0, 0, 0.12)" },
  "bg blur":  { "backdropFilter": "blur(24px)", "WebkitBackdropFilter": "blur(24px)" }
}
```

Light and dark themes are generated as a matched pair from the same source.

**Layout and logic are deliberately separated.** The generated component holds only styled primitives and markup. Anything a developer would actually edit is pushed into a companion hook, so a re-export from Figma does not clobber hand-written logic:

```ts
const useProductCard1 = () => {
  let data: any = { price: "$3333.333" };
  const handleClick = (): any => {};
  return { data, fns: { handleClick } };
};
```

**The regeneration contract is stated in the code.** Each generated file opens with a warning that editing it by hand forfeits conflict-free regeneration. That constraint, round-tripping between a design tool and a codebase without losing developer work, was the real subject of most enterprise conversations about the product.

**Where it stops.** Types come out as `any` until someone narrows them, and the generated CSS is absolute (`width: 417px`) rather than responsive. Both were standard questions from technical buyers, and both are visible right here in the output.
